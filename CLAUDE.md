# CLAUDE.md — правила для агентов

Этот файл обязателен к прочтению в начале **каждой** сессии. Он короткий специально: подробности лежат в `docs/`, здесь только то, что нельзя пропустить.

## Проект за 30 секунд

Автономное приложение для D&D-сессий онлайн. Мастер запускает один `.exe` (Go), игроки заходят по ссылке из браузера (клиент на TypeScript/React вшит в бинарник). Четыре системы: виртуальный стол, голос и видео (встроенный SFU), лист персонажа (D&D 5e 2024 / SRD 5.2), вики мастера.

Видение: [docs/vision.md](docs/vision.md) · Архитектура: [docs/architecture/overview.md](docs/architecture/overview.md) · Роадмап: [docs/roadmap.md](docs/roadmap.md)

## Язык

- Документация, Issues, описания PR — **на русском**.
- Код, идентификаторы, комментарии в коде, сообщения коммитов, имена веток — **на английском**.
- Строки интерфейса — только через i18n-ключи (`ru` по умолчанию, плюс `en`), никакого захардкоженного текста в компонентах.
- Термины берём из [docs/glossary.md](docs/glossary.md). Новый термин сначала добавляем туда.

## Интерфейс

Любая работа с UI клиента (страницы, компоненты, стили, раскладка, тексты интерфейса в `web/`) ведётся по [skills/frontend.md](skills/frontend.md): сначала короткий план (палитра, шрифты, раскладка, принципы), проверка плана против брифа, затем код и самокритика по скриншотам. Это относится и к архитектору (брифы на UI), и к исполнителю. Код без визуальной части (типы протокола, утилиты, store) этим правилом не затрагивается.

## Роли

Подробно: [docs/process/roles.md](docs/process/roles.md). Одновременно работает **один** агент.

- **Владелец** (пользователь) — приоритеты, ответы, согласование спек, мердж.
- **Архитектор** (сильная модель) — документация и ADR, Issues с **брифами** для исполнителя, **ревью** PR. Продуктовый код не пишет.
- **Исполнитель** (более слабая модель) — реализует ровно один бриф и открывает PR.

Определи свою роль по первому сообщению сессии. Если в нём есть «ты — исполнитель» или ссылка на бриф в Issue — ты исполнитель. Иначе ты архитектор.

Перед любой работой: `main` свежий, нет чужой незавершённой ветки (`git branch -a`, `gh pr list`). Если есть — спроси владельца.

## Если ты архитектор

1. **Спека раньше брифа.** Поведение, протокол, модель данных, архитектура — сначала в `docs/` (или ADR) и согласование с владельцем. Не хватает информации — `status:needs-spec` и вопрос владельцу.
2. **Бриф.** По [docs/process/brief-template.md](docs/process/brief-template.md), в теле Issue; затем `status:ready`. Все решения принимаешь ты, исполнитель ничего не выбирает.
3. **Ревью.** По [docs/process/review-checklist.md](docs/process/review-checklist.md): сам запускаешь проверки, вердикт APPROVE или CHANGES комментарием в PR.
4. Документацию правишь в ветках `docs/...` через PR, как и всё остальное.

## Если ты исполнитель

1. Прочитай бриф: `gh issue view <N>` (или правки: `gh pr view <M> --comments`). Прочитай только документы, указанные в брифе.
2. Делай **ровно** то, что в брифе. Не меняй `docs/`, `CLAUDE.md`, ADR, CI, не добавляй зависимости, не трогай файлы вне брифа, не «улучшай» соседний код.
3. Не оставляй заглушек, `TODO` и фиктивных тестов. Не ослабляй и не удаляй существующие тесты.
4. Неясно или бриф противоречит коду или спеке — **остановись**: вопрос комментарием в Issue, метка `status:blocked`, конец работы. Не угадывай.
5. Если задача затрагивает UI — работай по [skills/frontend.md](skills/frontend.md) (см. раздел «Интерфейс»), а план дизайна приложи к PR.
6. Перед PR выполни все «Критерии приёмки» брифа и [definition-of-done.md](docs/process/definition-of-done.md) в части «Код» и «Проверки».
7. PR: `Closes #N`, раздел «Отклонения от брифа», Issue получает `status:in-review`. Не мерджи.

## Общие правила git

- **Ветка:** `<type>/<issue>-<slug>`, например `feat/12-token-drag`. Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `spike`.
- **Коммиты:** [Conventional Commits](https://www.conventionalcommits.org/) на английском, в теле `Refs #12`. Мелкие осмысленные коммиты.
- **PR:** по шаблону `.github/PULL_REQUEST_TEMPLATE.md`. Мерджит **владелец** (squash), агент — только по его прямой просьбе.
- Полный процесс: [docs/process/workflow.md](docs/process/workflow.md).

## Жёсткие запреты

- Не пушить напрямую в `main`, не делать force-push в `main`, не переписывать опубликованную историю.
- Не коммитить секреты, токены, `.env`, пользовательские данные из `data/`.
- Не редактировать по существу ADR со статусом `accepted`. Решение меняется только новым ADR с полем `Supersedes`.
- Не добавлять игровой контент не из SRD 5.2 (никаких текстов из PHB/MM/DMG и других закрытых книг): это лицензионный риск.
- Не добавлять зависимость с CGO на сервере (сборка должна оставаться `CGO_ENABLED=0`).
- Не тянуть внешние CDN в клиент: приложение должно работать без интернета (кроме туннеля и STUN).
- Не создавать GitHub-репозитории, метки или релизы и не публиковать что-либо без явного согласия пользователя.
- Не добавлять зависимости с лицензией, несовместимой с AGPL-3.0 (см. [ADR-0007](docs/adr/0007-license-agpl-3.md)). Не мерджить сторонние PR, пока не введено CLA.


## Когда сомневаешься

Спроси пользователя. Задать вопрос дешевле, чем переделывать. Особенно это касается листа персонажа: детальные требования к нему пользователь ещё не дал.
