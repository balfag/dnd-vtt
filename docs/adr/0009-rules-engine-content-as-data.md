# ADR-0009: правила 5e как данные и поэтапный движок правил

- **Статус:** accepted (2026-10-16, владелец). Конкретная схема данных и источник SRD 5.2 уточняются по итогам spike #37 — дополнением, не новым решением
- **Дата:** 2026-10-16
- **Supersedes:** —

## Контекст
Владелец хочет интерактивный лист персонажа: создание персонажа мастером-помощником (вид, класс, уровень…), применение заклинаний и атак к целям с проверками и уроном по правилам, повышение уровня с мультиклассом — с возможностью всё это отключить. Плюс homebrew: свои черты, заклинания, оружие и т. д.

Ограничения:
- Встраивать можно только контент **SRD 5.2** (CC-BY-4.0, [ADR-0004](0004-dnd-5e-srd-5-2.md)). Остальное содержимое книги игрока закрыто; его пользователь может завести только сам, как homebrew.
- Значит, SRD и homebrew должны описываться **одним и тем же форматом**, иначе движок придётся писать дважды.

## Решение
- **Контент — это данные, а не код.** Виды, классы, подклассы, предыстории, черты, заклинания, предметы, монстры, состояния описываются декларативно (JSON по версионируемой схеме): характеристики, выборы, эффекты (бонусы, владения, урон, спасброски, области, длительности). Код движка (`internal/sheet/rules5e`) интерпретирует эти описания.
- **SRD 5.2** поставляется встроенным пакетом контента (`internal/compendium/data`), **homebrew** — пакетами контента в БД кампании по той же схеме. Редактор homebrew создаёт такие же записи, что лежат в SRD-пакете.
- **Поэтапная автоматизация**, каждый этап полезен сам по себе и отключается в настройках кампании:
  1. лист: ввод вручную, автоподсчёт производных значений, броски в чат;
  2. мастер создания персонажа по правилам (вид, класс, предыстория, характеристики, снаряжение);
  3. применение заклинаний и атак: выбор целей или области → броски атаки/спасброски (кубики бросает система или вводит игрок) → рекомендованный урон или эффект, применение по подтверждению;
  4. повышение уровня и мультикласс: система показывает только допустимые по правилам варианты.
- Кубики: по умолчанию бросает сервер (`crypto/rand`); игрок может ввести результат физического броска, такой бросок помечается в логе как «введён вручную».
- Модель «двух видов» (смешанное происхождение) в правилах 2024 отсутствует — поддерживается только как homebrew-правило кампании.

## Рассмотренные альтернативы
- **Правила в коде для каждого заклинания и класса:** быстро для первых записей, но homebrew становится невозможным без программиста.
- **Скриптовый язык для эффектов (Lua/JS):** гибко, но небезопасно для пользовательского контента и тяжело для проверки; декларативная схема с ограниченным набором эффектов покрывает почти всё SRD, исключения — особыми обработчиками в коде.
- **Импорт с D&D Beyond и других сервисов:** лицензионный риск, не-цель.

## Последствия
- Нужен spike: найти или собрать структурированный SRD 5.2 (есть ли открытый набор данных под совместимой лицензией; если нет — разбор PDF/текста SRD), спроектировать схему эффектов на реальных записях (≥ 20 заклинаний разных типов, 2 класса до 5 уровня, 3 вида). По итогам ADR переходит в `accepted` или правится.
- Перевод контента SRD на русский — отдельный пакет локализации контента.
- Листы NPC и монстров используют ту же схему (статблок — частный случай).
