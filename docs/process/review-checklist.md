# Чек-лист ревью (для архитектора)

Ревью — это не «прочитал диф». Архитектор **запускает** код и проверки сам и сверяет результат с брифом и спекой.

## 1. Подготовка
```powershell
git fetch origin
git switch <branch>
gh pr view <M>
gh issue view <N>        # бриф
git diff main...HEAD --stat
```

## 2. Соответствие брифу
- [ ] Сделано всё из «Сделать», ничего из «Не делать».
- [ ] Файлы, типы и сигнатуры совпадают с «Контрактами».
- [ ] Нет изменений в файлах, которых нет в брифе (особенно `docs/`, `CLAUDE.md`, конфиги CI, чужие пакеты).
- [ ] Нет новых зависимостей, кроме разрешённых в брифе. Лицензии совместимы с AGPL-3.0.
- [ ] Раздел «Отклонения от брифа» в PR заполнен честно; каждое отклонение обосновано.

## 3. Проверки (запустить самому)
- [ ] Все команды из «Критериев приёмки» брифа.
- [ ] Всё применимое из [definition-of-done.md](definition-of-done.md).
- [ ] Ручной сценарий, если в брифе есть UI или сеть.

## 4. Корректность
- [ ] Логика соответствует спеке в `docs/`, а не только брифу (бриф мог упустить деталь — тогда это ошибка брифа, фиксируем отдельно).
- [ ] Ошибки обрабатываются и оборачиваются, не проглатываются (`_ = err`, пустой `catch`).
- [ ] Ресурсы закрываются: файлы, соединения, `rows`, тикеры, горутины завершаются по `context`.
- [ ] Конкурентность: общие данные под мьютексом или в одной горутине; `go test -race` проходит.
- [ ] Граничные случаи: пустой ввод, дубликаты, большие значения, разрыв соединения, повторный вызов.
- [ ] Права и видимость проверяются на сервере (см. [security.md](../architecture/security.md)).
- [ ] Windows: пути через `filepath`, нет зависимостей от CRLF/LF и регистра.

## 5. Типичные ошибки слабых моделей — проверить отдельно
- [ ] **Заглушки:** `TODO`, `panic("not implemented")`, пустые функции, захардкоженные ответы «чтобы тест прошёл».
- [ ] **Фиктивные тесты:** тест ничего не проверяет, проверяет мок вместо кода, или тест подогнан под неверное поведение. Сломай код вручную — тест должен упасть.
- [ ] **Изменённые тесты:** существующие тесты ослаблены или удалены, чтобы «позеленело».
- [ ] **Выдуманные API:** вызовы несуществующих функций библиотек или параметров (проверить по `go doc` / типам TS).
- [ ] **Устаревшие API:** deprecated-функции, старые мажорные версии библиотек.
- [ ] **Скоуп-крип:** «попутные улучшения», переименования, переформатирование чужих файлов.
- [ ] **i18n:** захардкоженные строки в UI, ключи только в одном языке.
- [ ] **Секреты и мусор:** отладочные `fmt.Println`/`console.log`, закомментированный код, артефакты сборки в коммите.

## 6. Вердикт

Комментарий в PR (`gh pr comment <M> --body-file review.md`) в формате:

````markdown
## Ревью архитектора: APPROVE | CHANGES

### Проверено
- `go test -race ./...` — ok
- <что ещё запускал>

### Замечания
1. **[блокер]** `internal/ws/hub.go:84` — <что не так>. Почему: <последствие>. Как исправить: <конкретно>. Проверка: <команда/сценарий>.
2. **[важно]** ...
3. **[мелочь]** ... (не блокирует мердж)

### Ошибки брифа
<Если проблема возникла из-за неточного брифа — признать здесь и исправить бриф/спеку отдельно.>
````

- **APPROVE** — нет блокеров и важных замечаний. Снять статусную метку с Issue, сообщить владельцу, что можно мерджить.
- **CHANGES** — поставить `status:changes-requested`. Замечания пишутся как мини-бриф: исполнитель исправляет их, не перечитывая всю переписку.
- Если по одному PR больше двух кругов CHANGES — остановиться и пересмотреть бриф: вероятно, задача слишком большая или плохо описана.
