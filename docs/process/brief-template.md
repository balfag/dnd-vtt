# Шаблон брифа для исполнителя

Бриф — это промт для более слабой модели. Он должен быть **самодостаточным**: исполнитель не должен угадывать, принимать решения или читать половину `docs/`. Всё, что можно решить заранее, решает архитектор.

## Правила написания (для архитектора)

1. **Один бриф — один PR**, примерно до 300–400 строк изменений без учёта сгенерированных файлов. Больше — разбей на несколько Issues.
2. **Решения принимает архитектор.** Имена пакетов, файлов, типов, сигнатуры публичных функций, формат данных, библиотеки с версиями — всё указано явно.
3. **Контекст дозированно.** Перечисли 1–4 документа или раздела, которые нужно прочитать, а не «изучи docs/».
4. **Код-якоря.** Для нетривиальных мест дай сигнатуру, пример или псевдокод. Для стандартных вещей — короткое описание.
5. **Проверяемые критерии.** Каждый критерий проверяется командой или конкретным сценарием, а не словами «работает корректно».
6. **Явно назови, чего НЕ делать.** Слабые модели склонны расширять скоуп и «улучшать» соседний код.
7. **Типичные ловушки.** Если знаешь, где легко ошибиться (гонки, закрытие ресурсов, кодировки на Windows), — напиши об этом.
8. Пиши по-русски; идентификаторы, пути и команды — как в коде.

## Шаблон

Копируется в тело Issue целиком.

````markdown
## Бриф для исполнителя

### Цель
<1–3 предложения: что должно появиться и зачем.>

### Прочитай перед началом
- `CLAUDE.md` — раздел «Если ты исполнитель»
- `skills/frontend.md` — целиком, **если задача затрагивает UI** (иначе строку удалить)
- `docs/...#раздел` — <зачем>

### Ветка
`<type>/<issue>-<slug>`

### Скоуп
**Сделать:**
1. ...

**Не делать:**
- ...

### Файлы
| Файл | Действие | Содержимое |
|------|----------|------------|
| `internal/x/y.go` | создать | ... |
| `internal/x/y_test.go` | создать | тесты: ... |

### Контракты (не менять без согласования)
```go
// Сигнатуры, типы, форматы, которые должны получиться ровно такими.
```

### Пошагово
1. ...
2. ...

### Зависимости
- `module@vX.Y.Z` — зачем. Других зависимостей не добавлять.

### Тесты
- <какие случаи обязательно покрыть, включая граничные и ошибочные>

### Критерии приёмки
- [ ] `go test ./...` проходит
- [ ] <конкретная команда> выводит <конкретный результат>
- [ ] <сценарий ручной проверки>

### Ловушки
- ...

### Если что-то неясно
Остановись. Не придумывай. Напиши вопрос комментарием в эту Issue (`gh issue comment <N>`), поставь `status:blocked` и закончи работу.

### Результат
PR в `main` по шаблону, заголовок `<type>(<scope>): ...`, в описании `Closes #<N>` и раздел «Отклонения от брифа» (пустой, если их нет). Поставь Issue метку `status:in-review`.
````
