# Сеть и подключение

> Статус: `draft`. Ключевой риск проекта. Решение: [ADR-0005](../adr/0005-connectivity-ports-and-tunnel.md) — ждёт внешних тестов spike #8 ([отчёт](../../spikes/connectivity/REPORT.md)); HTTPS в LAN — [ADR-0015](../adr/0015-lan-https-self-signed.md).

## Порты

| Порт (по умолчанию) | Протокол | Назначение |
|---------------------|----------|------------|
| `7777` | TCP | HTTPS и HTTP (HTTP — только с loopback), WebSocket, раздача клиента и ассетов. Флаг `-http-addr` |
| `7778` | UDP | WebRTC-медиа (ICE UDP mux: все участники на одном порту). Флаг `-media-port` (`DNDVTT_MEDIA_PORT`) |
| `7778` | TCP | ICE-TCP (фолбэк для медиа, если UDP заблокирован) |

Все порты настраиваются. Задача — **минимум портов**: мастер пробрасывает `7777/tcp` и `7778/udp+tcp`. Встроенный TURN не нужен (spike #8): в M2 его нет, окончательно решает ADR-0005.

Медиа-порт слушается на всех интерфейсах. В ICE-кандидаты сервера попадают адреса интерфейсов (как в списке LAN-адресов ADR-0015, плюс loopback для клиента мастера); подстановка внешнего адреса — M5.

## Режим 1: проброс портов (ручной)

- Мастер пробрасывает порты на роутере на свой ПК.
- Приложение узнаёт внешний IP (STUN-запрос или публичный сервис определения IP) и проставляет его в ICE-кандидаты (`SetNAT1To1IPs`).
- **Мастер подключения** в UI: показывает локальный IP, нужные порты, инструкцию и кнопку «Проверить доступность». Проверка извне требует внешнего помощника; варианты: STUN-ответ плюс подсказка «попросите игрока открыть ссылку», или собственный бесплатный эхо-сервис (позже).
- Проблемы: CGNAT у провайдера (проброс невозможен), двойной NAT. В этом случае UI предлагает туннель.

## Режим 2: встроенный туннель

**Проблема:** популярные HTTP-туннели (Cloudflare Quick Tunnel, `ngrok http`) пропускают только HTTP/WebSocket. WebRTC-медиа (UDP) через них не проходит.

Варианты (выбор делаем по итогам spike):

| Вариант | Как | Плюсы | Минусы |
|---------|-----|-------|--------|
| A. Туннель с TCP+UDP (playit.gg) | Агент playit пробрасывает и HTTP-, и UDP-порт | Медиа идёт напрямую по UDP, минимальная задержка | Внешняя зависимость, нужен аккаунт, бесплатный тариф ограничен |
| B. HTTP-туннель + медиа через WebSocket-TURN | Клиент подключается к встроенному TURN по TCP/TLS, проложенному через тот же туннель | Работает с Cloudflare, без аккаунта | Медиа по TCP — больше задержка, нагрузка на туннель; нужна проверка совместимости TURN-over-WS |
| C. TCP-туннель (`ngrok tcp`, bore) для ICE-TCP | Медиа по ICE-TCP через TCP-туннель | Проще, чем B | Требует аккаунта (ngrok), задержка TCP |

Spike в M0 должен ответить: какой вариант даёт рабочие 8 камер при задержке до 300 мс, сколько это стоит пользователю, можно ли встроить агент туннеля в наш бинарник или запускать его как sidecar.

## HTTPS

Браузеры дают доступ к микрофону и камере (`getUserMedia`) только в **secure context**: HTTPS или `localhost`.
- **Туннель** даёт HTTPS автоматически.
- **Проброс портов:** нужен TLS. Варианты: самоподписанный сертификат (предупреждение в браузере у игроков — плохой UX), Let's Encrypt через бесплатный DNS-сервис (sslip.io/nip.io + HTTP-01 challenge на 80-м порту), собственный DDNS. **Открытый вопрос, решается в spike M0.**

### HTTPS в локальной сети (M2)

Решено в [ADR-0015](../adr/0015-lan-https-self-signed.md): HTTPS и HTTP на одном порту, самоподписанный сертификат в папке данных, HTTP только с loopback, ссылка на игру — с LAN-адресом. Игрок один раз принимает предупреждение браузера.

## STUN

Используем публичный STUN (например, `stun.l.google.com:19302`) только для определения внешнего адреса. Медиа через внешние серверы не идёт.

## Определение внешнего адреса

Приоритет при формировании ссылки на игру:
1. Адрес активного туннеля.
2. Адрес, вручную заданный мастером (домен или DDNS).
3. Внешний IP, полученный через STUN.
4. LAN-IP (для игры в одной сети).
