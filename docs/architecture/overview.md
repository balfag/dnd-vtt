# Архитектура: обзор

> Статус: `review`. Решения: [ADR-0001](../adr/0001-go-server-ts-client.md), [ADR-0002](../adr/0002-embedded-sfu-pion.md), [ADR-0003](../adr/0003-sqlite-pure-go.md), [ADR-0008](../adr/0008-accounts-and-game-sessions.md)

## Принципы

1. **Один процесс, один файл.** Всё серверное — в одном Go-бинарнике, клиент вшит через `go:embed`. Сборка `CGO_ENABLED=0`.
2. **Сервер авторитетен.** Клиент шлёт намерения (`token.move`), сервер проверяет права, применяет изменение и рассылает результат с учётом видимости.
3. **Видимость фильтруется на сервере.** Игроку физически не приходит то, чего он не должен видеть: GM-слой, скрытые фишки, вики, броски `gm`/`blind`.
4. **Офлайн-first.** Никаких внешних CDN и обращений в интернет, кроме STUN и туннеля.
5. **Модульность по системам.** Каждая система (vtt, av, wiki, sheet) — отдельный пакет с явным интерфейсом и без циклических импортов.

## Стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Сервер | Go 1.26+ | Один статический бинарник, сильный WebRTC-стек (pion), простая кросс-компиляция |
| HTTP/WS | `net/http` + `github.com/coder/websocket` | Стандартная библиотека и минимальная зависимость |
| БД | SQLite через `modernc.org/sqlite` | Без CGO, файл в папке данных, WAL |
| Пароли | argon2id из `golang.org/x/crypto/argon2` | Чистый Go, рекомендация OWASP, см. [ADR-0008](../adr/0008-accounts-and-game-sessions.md) |
| Миграции | Встроенные `.sql` + свой раннер в `internal/store` | Версионирование схемы без лишней зависимости, правила — в [data-model.md](data-model.md#миграции) |
| WebRTC | `pion/webrtc` v4, `pion/turn` | Встраиваемый SFU и TURN |
| Клиент | TypeScript, React, Vite | Массовый стек, хорошо знаком агентам |
| Холст | PixiJS v8 ([ADR-0012](../adr/0012-pixijs-scene-canvas.md)) | WebGL-рендер тысяч объектов, панорама и зум |
| Состояние клиента | Zustand | Простое глобальное хранилище |
| Редактор вики | TipTap (ProseMirror) | Блочный редактор с расширениями (упоминания, таблицы) |
| i18n | i18next + react-i18next | Стандарт |
| Тесты | `go test`; Vitest; Playwright для e2e ([ADR-0013](../adr/0013-playwright-e2e.md)) | |
| Пакетный менеджер | pnpm | Быстрый, строгий lock-файл |

## Раздача клиента

Собранный клиент (`pnpm -C web build` → `web/dist`) встроен в бинарник и раздаётся сервером по правилам:

| Запрос | Ответ |
|--------|-------|
| `GET /api/...` | REST-маршруты; неизвестный путь — `404`, а не SPA |
| `GET /static/<file>` | файл сборки Vite (имена с хешем), `Cache-Control: public, max-age=31536000, immutable` |
| существующий файл из `dist` | этот файл, `Cache-Control: no-cache` |
| путь с расширением, которого нет в `dist` (`/favicon.ico`) | `404` |
| путь с сегментом, начинающимся с точки (`/.gitkeep`) | `404` |
| любой другой путь (`/`, `/play/abc`) | `index.html`, `Cache-Control: no-cache` — маршрутизирует сам клиент |
| клиент не собран (нет `index.html`) | `503` с подсказкой `pnpm -C web build` |

Ассеты сборки лежат в `/static/`, потому что `/assets/` занят файлами кампании.

`Content-Type` файлов клиента задаётся фиксированной таблицей по расширению (`internal/httpapi/spa.go`), а не через `mime.TypeByExtension`: на Windows тот читает реестр, где у `.js` бывает `text/plain`, и браузер отказывается выполнять модульные скрипты. Это же правило действует для всего, что сервер отдаёт из встроенных файлов.

В режиме разработки клиент обслуживает Vite dev server (`http://localhost:5173`), он проксирует `/api` и `/ws` на Go-сервер (`localhost:7777`).

## Жизненный цикл

1. Мастер запускает `dndvtt.exe`. Создаётся папка данных (по умолчанию `%APPDATA%/dndvtt` на Windows, `./data` в dev-режиме), применяются миграции.
2. Поднимаются HTTP (TCP-порт, по умолчанию `7777`) и медиа (UDP+TCP-порт, по умолчанию `7778`).
3. Открывается браузер мастера: на первом запуске — `http://localhost:7777/setup` (мастер задаёт логин и пароль), дальше — `http://localhost:7777/?gm=<одноразовый токен>`, который сразу входит мастером. С других устройств мастер входит логином и паролем.
4. Мастер выбирает кампанию и начинает игровую сессию. Сервер определяет внешний адрес (проброс или туннель, см. [networking.md](networking.md)) и показывает ссылку на игру; новая игровая сессия делает старую ссылку недействительной.
5. Игроки открывают ссылку, входят или регистрируются (см. [security.md](security.md)), подключаются по WebSocket, получают снапшот состояния в пределах своей видимости, затем поток изменений.
6. При закрытии приложения выполняется graceful shutdown: соединения закрываются с кодом `1001`, БД закрывается.

В dev-режиме (`-dev`) и в тестах при пустой базе создаётся тестовая кампания; в обычном режиме кампании создаёт только мастер.
