# Протокол клиент ↔ сервер

> Статус: `review` для разделов «REST» (включая «Ассеты (M1)»), «WebSocket: транспорт», «Конверт», «Синхронизация», «Сообщения M0», «Закрытие соединения», «Типы в Go и TS», «Сообщения M1: стол» (кроме «Инициатива»); «Инициатива» и каталог после M1 — `draft`.

Термины: **сессия входа** — вход на устройстве (cookie), **игровая сессия** — игровая встреча, **соединение** — одно WebSocket-подключение вкладки. См. [ADR-0008](../adr/0008-accounts-and-game-sessions.md).

## REST

Всё, что не интерактивно: вход, кампании, игровые сессии, загрузки, экспорт. JSON в теле запроса и ответа, `Content-Type: application/json`. Изменяющие запросы проверяют `Origin` (см. [security.md](security.md#csrf-и-websocket)).

Ошибка — всегда `{"error": {"code": "<code>", "message": "<текст для логов, не для UI>"}}` с HTTP-статусом:

| Код | HTTP | Когда |
|-----|------|-------|
| `bad_request` | 400 | невалидный JSON, нарушены ограничения полей |
| `invalid_credentials` | 401 | неверный логин или пароль |
| `unauthorized` | 401 | нет или истекла сессия входа |
| `forbidden` | 403 | нет прав, неверный `Origin`, не loopback там, где нужен loopback |
| `no_active_game` | 403 | ссылка на игру недействительна или игра не идёт |
| `removed` | 403 | участник удалён мастером |
| `not_found` | 404 | |
| `conflict` | 409 | логин занят, аккаунт мастера уже создан |
| `too_large` | 413 | тело запроса больше лимита |
| `unsupported_media_type` | 415 | тип загружаемого файла не разрешён |
| `rate_limited` | 429 | превышен лимит, есть `Retry-After` |
| `internal` | 500 | |

Клиент показывает пользователю текст по `code` из i18n, `message` не показывает.

### Вход и аккаунты (M0)

| Метод и путь | Кто | Тело → ответ |
|--------------|-----|--------------|
| `GET /api/setup` | loopback | → `{"needed": bool}` — нужен ли первый запуск |
| `POST /api/setup` | loopback, нет аккаунта мастера | `{"setupToken","login","password"}` → `201`, cookie, `Me` |
| `POST /api/auth/gm-token` | loopback | `{"token"}` → `200`, cookie, `Me` |
| `POST /api/auth/login` | все | `{"login","password","gameLink"?}` → `200`, cookie, `Me`. Без `gameLink` — только для мастера. С `gameLink` ссылка проверяется **до** пароля: недействительная → `403 no_active_game`; мастер с действующей ссылкой получает обычную сессию мастера |
| `POST /api/auth/register` | по ссылке на игру | `{"gameLink","login","password","displayName"}` → `201`, cookie, `Me` |
| `POST /api/auth/logout` | вошедший | → `204`, cookie удалена |
| `GET /api/auth/me` | вошедший | → `Me` или `401 unauthorized` |
| `POST /api/auth/password` | вошедший | `{"current","new"}` → `204` |
| `GET /api/game-links/{token}` | все | → `{"campaignName"}` или `403 no_active_game` — что показать на `/play/<token>` |
| `POST /api/password-resets/{token}` | все | `{"new"}` → `204` |

`Me`:
```jsonc
{
  "accountId": "01J…",
  "login": "anna",
  "isGm": false,
  "player": { "id": "01J…", "campaignId": "01J…", "displayName": "Анна", "color": "#3366ff", "role": "player" } // null у мастера вне игры
}
```

### Мастер (M0)

| Метод и путь | Тело → ответ |
|--------------|--------------|
| `GET /api/campaigns` | → `[{"id","name","createdAt","activeGameSession"}]`, `activeGameSession` — `{"id","startedAt"}` или `null` |
| `POST /api/campaigns` | `{"name"}` → `201` кампания |
| `PATCH /api/campaigns/{id}` | `{"name"}` → кампания |
| `POST /api/campaigns/{id}/game-sessions` | → `201` `{"id","campaignId","startedAt","link"}`; активная игровая сессия, если была, завершается |
| `POST /api/game-sessions/{id}/end` | → `204` |
| `POST /api/game-sessions/{id}/link` | → `{"link"}` — новая ссылка, старая перестаёт работать |
| `GET /api/campaigns/{id}/players` | → `[{"id","accountId","accountLogin","displayName","color","role","removed"}]`; `"online"` — есть ли у участника открытое WebSocket-соединение сейчас |
| `POST /api/players/{id}/remove` | → `204` |
| `POST /api/accounts/{id}/password-resets` | → `201` `{"link","expiresAt"}` |

`link` — полный URL (`<внешний адрес>/play/<token>`). До решения spike #8 внешний адрес — это схема и хост, по которым мастер открыл приложение. Время во всех ответах — unix-миллисекунды. Токен возвращается только в момент создания; сервер хранит лишь хеш, поэтому показать ссылку повторно нельзя — только сменить.

### Ассеты (M1)

| Метод и путь | Кто | Тело → ответ |
|--------------|-----|--------------|
| `POST /api/campaigns/{id}/assets` | мастер | `multipart/form-data`: `file` (обязательно), `kind` (`map` \| `token` \| `portrait` \| `handout` \| `other`, по умолчанию `other`) → `201 Asset`; если в кампании уже есть файл с тем же `sha256` — `200` и существующий `Asset` (новый `kind` не применяется) |
| `GET /api/campaigns/{id}/assets` | мастер | → `[Asset]`, новые первыми |
| `DELETE /api/assets/{id}` | мастер | → `204`; `409 conflict`, если ассет используется (фон сцены, изображение фишки) |
| `GET /assets/{id}` | вошедший с доступом | → байты файла (см. ниже) |

`Asset`:
```jsonc
{ "id": "01J…", "campaignId": "01J…", "kind": "map", "mime": "image/webp", "size": 1834221,
  "width": 3000, "height": 2000, "originalName": "tavern.webp", "createdAt": 1760530000000, "url": "/assets/01J…" }
```

Загрузка:
- Части читаются потоком, по порядку: `kind` (если есть) должен идти **до** `file`; неизвестная часть до `file` — `400`; всё после `file` не читается.
- Файл — не больше **50 МиБ** (тело запроса — не больше 50 МиБ + 1 МиБ на заголовки частей); больше — `413 too_large` (сервер прекращает чтение, не дожидаясь конца тела).
- Тип определяется **по содержимому** (первые байты), расширение и `Content-Type` части игнорируются: `image/png`, `image/jpeg`, `image/webp`, `image/gif`. Остальное — `415 unsupported_media_type` (SVG тоже: см. [security.md](security.md#загрузка-файлов)).
- Размеры изображения читаются из заголовка файла без полного декодирования; больше 16384 по любой стороне или не читается — `400 bad_request`.
- `originalName` — имя части `file` без пути, обрезанное до 200 символов; используется только для показа.
- Файл пишется во временный файл в той же папке и переименовывается в `<data>/campaigns/<campaign_id>/assets/<sha256>.<ext>` (`ext` — по типу: `png`, `jpg`, `webp`, `gif`); строка в БД добавляется после переименования.
- `DELETE` удаляет строку и файл.

Раздача `GET /assets/{id}`:
- Мастер — любой ассет. Игрок — только ассет своей кампании, который сейчас **фон активной сцены** или **изображение видимой ему фишки** на ней (правило видимости — «Сообщения M1»); handout'ы — в M3. Иначе — `404 not_found` (не `403`: не подтверждаем существование).
- Заголовки: `Content-Type` из БД, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: private, max-age=31536000, immutable`, `ETag: "<sha256>"`; `If-None-Match` → `304`.

## WebSocket: транспорт

- Одно соединение на вкладку: `wss://<host>/ws` (`ws://` по HTTP в LAN).
- Рукопожатие требует действующую сессию входа (cookie) и проверяет `Origin`; иначе `401`/`403` без апгрейда.
- Игрок подключается только в активную игровую сессию; мастер без активной игровой сессии получает соединение, но снапшот без игры (`game: null`).
- JSON-текстовые фреймы, не больше 64 КиБ. Бинарные фреймы не используются: ассеты идут через REST.
- Библиотека — `github.com/coder/websocket`.

## Конверт

```jsonc
{
  "t": "token.move",        // тип: <домен>.<действие>
  "id": "c-42",             // id команды клиента, опционально; уникален в пределах соединения
  "re": "c-42",             // в ответе сервера — id команды, на которую отвечаем
  "seq": 1532,              // номер события (только в событиях)
  "d": { ... }              // данные; может отсутствовать
}
```

- **Команда** (клиент → сервер): `t` + `id` + `d`.
- **Ответ** (сервер → клиент): `t: "ack"` или `t: "error"` с `re`. Ответ приходит только на команды с `id`.
- **Событие** (сервер → клиенты): `t` + `seq` + `d`. Рассылается только тем, кому разрешено видеть.

Ошибка: `{ "t": "error", "re": "c-42", "d": { "code": "forbidden", "message": "..." } }`.
Коды ошибок в WS: `bad_request`, `forbidden`, `not_found`, `conflict`, `rate_limited`, `internal`.

## Синхронизация

- `seq` — номер события **внутри игровой сессии**: начинается с `1` и растёт на единицу; новая игровая сессия начинает счёт заново.
- Сервер хранит в памяти буфер последних 1000 событий игровой сессии, но не старше 5 минут.
- Порядок:
  1. После подключения клиент шлёт `sync.hello`.
  2. Если `gameSessionId` и `lastSeq` из `hello` совпадают с текущей игровой сессией и все события после `lastSeq` есть в буфере, сервер досылает их по порядку. Иначе отправляет `sync.snapshot`.
  3. Далее приходят события с растущим `seq`. Клиент, заметивший пропуск `seq`, закрывает соединение и подключается заново с последним полученным `seq`.
- **Гарантия порядка.** `seq` событию и снапшоту сервер присваивает под одной блокировкой: всё, что произошло до снапшота, в нём уже учтено и имеет `seq ≤ snapshot.seq`; события с `seq ≤ snapshot.seq` клиент игнорирует. События применяются как «вставить или обновить», повторное событие о том же объекте безопасно.
- При смене или завершении игровой сессии соединения игроков закрываются с `4004`, а соединения мастера остаются и получают новый `sync.snapshot` (`seq` новой игры начинается с `0`).
- До `sync.hello` сервер принимает только `ping`; любую другую команду отклоняет `bad_request`.

**Оптимистичные обновления (M1):** клиент сразу показывает перемещение своей фишки; при `error` откатывает изменение. Перетаскивание во время движения шлётся с троттлингом (около 20 Гц) как `token.drag` (не сохраняется в БД), финальная позиция — как `token.move` (сохраняется).

## Сообщения M0

### `sync.hello` (C→S, команда)
```jsonc
{ "t": "sync.hello", "id": "c-1", "d": { "gameSessionId": "01J…", "lastSeq": 17 } } // оба поля опциональны
```
Ответ — `ack` с `{"resumed": true|false}`; при `false` следом приходит `sync.snapshot`.

### `sync.snapshot` (S→C, событие без `seq`)
```jsonc
{
  "t": "sync.snapshot",
  "d": {
    "seq": 17,                       // последний seq игровой сессии, 0 если событий не было
    "me": { "accountId": "01J…", "isGm": false, "playerId": "01J…" }, // playerId: null у мастера вне игры
    "game": {                        // null, если игровой сессии нет (только у мастера)
      "gameSessionId": "01J…",
      "startedAt": 1760530000000,
      "campaign": { "id": "01J…", "name": "Проклятие Страда" },
      "players": [ { "id": "01J…", "displayName": "Анна", "color": "#3366ff", "role": "player", "online": true } ] // без удалённых мастером
    }
  }
}
```
Поля M1 — в «Сообщения M1: стол» → «Снапшот в M1».

### `presence.update` (S→C, событие)
```jsonc
{ "t": "presence.update", "seq": 18, "d": { "playerId": "01J…", "online": false } }
```
Рассылается всем в игровой сессии при первом подключении участника и после закрытия его последнего соединения. Участник с двумя вкладками онлайн, пока открыта хотя бы одна. Новый участник (регистрация или первый вход в кампанию во время игры) приходит как `presence.update` с полями игрока: `{"playerId","online":<сейчас подключён?>,"player":{...как в snapshot}}`; сразу после регистрации это обычно `false`, а его подключение придёт отдельным событием `online: true`. Удалённый мастером участник получает закрытие `4003`, остальным приходит `online: false`.

### `ping` / `pong`
Клиент шлёт `{"t":"ping","id":"p-5"}` каждые 20 секунд, сервер отвечает `{"t":"pong","re":"p-5"}`. Сервер закрывает соединение, если 60 секунд от клиента не было ни одного сообщения.

### `ack`
`{"t":"ack","re":"c-1","d":{...}}` — `d` зависит от команды, для большинства команд отсутствует.

## Закрытие соединения

| Код | Причина | Что делает клиент |
|-----|---------|-------------------|
| `1000` | нормальное закрытие | — |
| `1001` | сервер останавливается | переподключается с паузой |
| `1003` | пришёл двоичный фрейм | переподключается; это ошибка клиента, пишет в консоль |
| `1009` | фрейм больше 64 КиБ | переподключается; это ошибка клиента, пишет в консоль |
| `1011` | внутренняя ошибка сервера при подключении | переподключается с паузой |
| `1013` | клиент не успевает читать (очередь отправки переполнена) | переподключается с паузой |
| `4001` | сессия входа отозвана или истекла | переходит на страницу входа |
| `4003` | участник удалён мастером | показывает «доступ закрыт мастером» |
| `4004` | игровая сессия завершена или сменилась | показывает «игра завершена» |
| `4008` | нет сообщений 60 секунд | переподключается |
| `4029` | превышен лимит сообщений | переподключается с паузой |

Невалидный JSON или конверт (`t` не строка, неизвестный `t`) — `error` `bad_request` с `re`, если `id` удалось прочитать; соединение не закрывается.

Переподключение — с экспоненциальной паузой от 0,5 до 10 секунд и случайным разбросом.

## Типы в Go и TS

- Go: структуры сообщений в `internal/ws/protocol`.
- TS: типы и type guard'ы в `web/src/shared/protocol`, пишутся вручную. Генератор (`tygo`) не используем: протокол небольшой, лишняя зависимость в сборке не нужна.
- Сверка: Go-тест пишет эталонные примеры каждого сообщения в `internal/ws/protocol/testdata/*.json` (обновление по флагу `-update`, файлы коммитятся); Vitest-тест в `web/src/shared/protocol` читает эти файлы и проверяет, что type guard каждого сообщения их принимает. Расхождение формата роняет тест на одной из сторон.

## Сообщения M1: стол

> Модель данных — [data-model.md](data-model.md); правила видимости — [security.md](security.md#авторизация).

### Когда команды M1 работают

Все команды M1 требуют **активной игровой сессии**: без неё (`game: null` у мастера) — `error` `conflict`. Подготовка сцен вне игры — позже, вместе с экраном кампании; до тех пор мастер готовит сцены, начав игровую сессию и не раздавая ссылку.

### Отрисовка события для получателя

В M1 события зависят от того, **кто их получает**: игрок не должен узнать о скрытой фишке. При этом `seq` — общий для игровой сессии, и клиент по пропуску номера переподключается. Поэтому:

- каждое событие с `seq` доставляется **каждому** подписанному соединению, но **отрисовывается для получателя** (роль, `playerId`): то, что получателю видеть нельзя, превращается в другое событие или в `{"t":"sync.noop","seq":N}` — «номер занят, для вас ничего»;
- буфер для продолжения хранит не готовые кадры, а событие и правило его отрисовки: при продолжении события отрисовываются заново для этого получателя;
- **преходящие** сообщения (`token.dragging`, `ping.shown`, `ruler.shown`) идут **без `seq`**, не буферизуются и не сохраняются; пропуск их не страшен.
- команды стола выполняются **по одной** на игровую сессию: изменение в БД и выдача `seq` его событиям не перемежаются с другой командой, поэтому порядок событий совпадает с порядком изменений;
- события, порождённые командой, приходят автору **раньше** её `ack`;
- команда без `id` не получает ни `ack`, ни `error` (так шлются `token.drag` и `ruler.update`).

### Координаты и единицы

- Координаты сцены — пиксели исходного изображения фона (`0,0` — левый верхний угол), числа с плавающей точкой.
- Фишка: `x`, `y` — **центр**; `w`, `h` — размер **в клетках** (`0.5` Tiny, `1` Medium, `2` Large…); `rotation` — градусы по часовой стрелке.
- Фигуры (`shape`): `{"type":"rect","x","y","w","h"}`, `{"type":"polygon","points":[[x,y],…]}` (3–200 точек), `{"type":"circle","x","y","r"}`.

### Снапшот в M1

К `game` в `sync.snapshot` (см. «Сообщения M0») добавляются:

```jsonc
"activeSceneId": "01J…",            // null, если активной сцены нет
"scenes": [ { "id", "name", "sort" } ], // только мастеру; игроку — []
"scene": { …SceneView… },           // активная сцена, отрисованная для получателя; null, если активной нет
"chat": [ …ChatMessage… ]           // последние 50 сообщений, видимых получателю, по возрастанию времени
```

`SceneView`:
```jsonc
{
  "id": "01J…", "name": "Таверна", "width": 3000, "height": 2000,
  "grid": { "type": "square", "sizePx": 70, "unitFt": 5, "offsetX": 0, "offsetY": 0, "color": "#9aa8b3", "visible": true },
  "background": { "assetId": "01J…", "url": "/assets/01J…" },   // или null
  "fog": { "enabled": true, "ops": [ { "op": "reveal", "shape": {…} } ] }, // ops — по порядку применения
  "tokens":   [ …Token… ],   // только видимые получателю
  "drawings": [ …Drawing… ]
}
```
`grid.type`: `square` | `hexPointy` (вершина сверху) | `hexFlat` (вершина сбоку). Ограничения полей — [data-model.md](data-model.md#scene).

`Token`:
```jsonc
{
  "id": "01J…", "sceneId": "01J…", "layer": "tokens",           // map | tokens | gm
  "x": 350, "y": 210, "w": 1, "h": 1, "rotation": 0, "z": 3,
  "name": "Гоблин", "nameVisibility": "hover",                   // all | hover | gm
  "image": { "assetId": "01J…", "url": "/assets/01J…" },         // или null
  "hidden": false, "locked": false,
  "owners": [ "01J…" ],                                          // playerId
  "bars": [ { "key": "hp", "value": 7, "max": 7, "visibility": "owners" } ], // all | owners | gm
  "conditions": [ "prone" ]
}
```
Игроку фишка отдаётся **без** полей, которые ему не положены: `name` при `nameVisibility: "gm"` — пустая строка; полоски с `visibility`, которая ему не разрешена, — не попадают в массив.

`Drawing`:
```jsonc
{ "id": "01J…", "sceneId": "01J…", "kind": "freehand", "data": {…}, "color": "#c9a34e", "authorPlayerId": "01J…" }
```
`kind`: `freehand` (`data.points`), `rect`, `circle`, `text` (`data.text`, `data.x`, `data.y`, `data.size`), `template` (`data.shape`: `cone` | `sphere` | `line` | `cube` | `cylinder`, `data.x`, `data.y`, `data.size` в футах, `data.direction` в градусах).

### Видимость фишки для игрока

Мастер видит всё. Игроку фишка на активной сцене видна, если `layer != "gm"` и выполнено одно из двух:
1. игрок — в `owners` фишки (свою фишку видно всегда, даже `hidden` и в тумане);
2. `hidden == false` **и** (туман сцены выключен **или** центр фишки раскрыт). Центр раскрыт, если последняя по порядку операция в `fog.ops`, фигура которой содержит центр, — `reveal`; точка вне всех фигур скрыта. Точка на границе фигуры считается внутри.

### Сцены (только мастер)

| Команда | Данные | Ответ `ack` | Событие |
|---------|--------|-------------|---------|
| `scene.create` | `{ "name", "width"?, "height"?, "grid"? }` | `{ "sceneId" }` | `scenes.changed`; если активной сцены нет — затем `scene.activated` |
| `scene.update` | `{ "sceneId", "name"?, "width"?, "height"?, "grid"?, "backgroundAssetId"? }` (`null` — убрать фон) | — | `scene.changed` |
| `scene.delete` | `{ "sceneId" }`; активную удалить нельзя → `conflict` | — | `scenes.changed` |
| `scene.reorder` | `{ "sceneIds": [ … ] }` — полный порядок | — | `scenes.changed` |
| `scene.activate` | `{ "sceneId" }` | — | `scene.activated` |
| `scene.view` | `{ "sceneId" }` — что смотрит **этот** мастерский клиент | `{ "scene": SceneView }` | — |

События:
- `scenes.changed` — `{ "scenes": [ { "id", "name", "sort" } ] }`; мастеру как есть, игроку — `sync.noop`.
- `scene.changed` — `{ "scene": SceneView без tokens и drawings }`; игроку — только если это активная сцена, иначе `sync.noop`.
- `scene.activated` — `{ "scene": SceneView }` отрисованная для получателя (игрок получает новую сцену целиком).

Мастер получает события **всех** сцен (его отрисовка не фильтрует); какую сцену показывать, решает его клиент. `scene.view` нужен, чтобы получить сцену целиком (фишки, рисунки) при переключении просмотра; в снапшоте мастера `scene` — активная, а при реконнекте клиент повторяет `scene.view` для сцены, которую смотрел.

### Фишки

| Команда | Кто | Данные | Событие |
|---------|-----|--------|---------|
| `token.create` | мастер | `{ "sceneId", …поля Token без id }` → `ack { "tokenId" }` | `token.changed` |
| `token.update` | мастер | `{ "tokenId", …изменяемые поля }` | `token.changed` |
| `token.move` | мастер или владелец (если не `locked`) | `{ "tokenId", "x", "y" }` | `token.changed` |
| `token.drag` | мастер или владелец (если не `locked`) | `{ "tokenId", "x", "y" }`, **без `id`** (ответа нет); клиент шлёт не чаще 20 в секунду | `token.dragging` (преходящее) |
| `token.delete` | мастер | `{ "tokenId" }` | `token.removed` |

События:
- `token.changed` — `{ "token": Token }`, отрисовывается для получателя: видна → `token.changed` с урезанными полями; не видна → `token.removed { "tokenId" }` (клиент удаляет, если знал; если не знал — игнорирует). Игроку — только для активной сцены, иначе `sync.noop`.
- `token.removed` — `{ "tokenId" }`.
- `token.dragging` — `{ "tokenId", "x", "y" }` без `seq`, только тем, кому фишка видна.
- Координаты `x`, `y` — в пределах сцены (`0..width`, `0..height`), иначе `bad_request`.
- Перемещение игроком своей фишки в нераскрытый туман допустимо: фишка остаётся видна владельцу; другим игрокам — по правилу видимости.

### Туман (только мастер)

| Команда | Данные | Событие |
|---------|--------|---------|
| `fog.set` | `{ "sceneId", "enabled" }` | `fog.changed` |
| `fog.reveal` | `{ "sceneId", "shape" }` | `fog.changed` |
| `fog.hide` | `{ "sceneId", "shape" }` | `fog.changed` |
| `fog.reset` | `{ "sceneId" }` — убрать все операции (всё скрыто) | `fog.changed` |

`fog.changed` — `{ "sceneId", "fog": { "enabled", "ops" }, "tokens"? }`. Мастеру — без `tokens`. Игроку — только для активной сцены (иначе `sync.noop`), и **с `tokens`**: полный список фишек сцены, видимых ему после изменения; клиент заменяет им свой список. Так смена видимости десятков фишек — одно событие, а не поток `token.changed`/`token.removed`.

Операций в сцене — не больше 500; при превышении — `conflict` (уплотнение — позже). `fog.reset` очищает список.

### Рисунки и шаблоны областей

| Команда | Кто | Данные | Событие |
|---------|-----|--------|---------|
| `drawing.create` | любой участник | `{ "sceneId", "kind", "data", "color" }` → `ack { "drawingId" }` | `drawing.changed` |
| `drawing.update` | автор или мастер | `{ "drawingId", "data"?, "color"? }` | `drawing.changed` |
| `drawing.delete` | автор или мастер | `{ "drawingId" }` | `drawing.removed` |

Рисунки — это слой `drawings`: видны всем на сцене; игроку — только на активной (команда игрока по неактивной сцене — `forbidden`). Размер `data` в JSON — до 16 КиБ, точек в `freehand` — до 2000, текст — до 500 символов.

### Пинг и линейка (преходящие)

| Команда | Данные | Событие |
|---------|--------|---------|
| `ping.place` | `{ "sceneId", "x", "y", "focus"? }` (`focus` — только мастер: перевести камеры игроков) | `ping.shown { "playerId", "sceneId", "x", "y", "focus" }` |
| `ruler.update` | `{ "sceneId", "points": [[x,y],…] }` (до 50 точек), не чаще 20 в секунду | `ruler.shown { "playerId", "sceneId", "points" }` |
| `ruler.clear` | `{ "sceneId" }` | `ruler.shown { "playerId", "sceneId", "points": [] }` |

Все — без `seq`, всем на этой сцене (игрокам — только на активной).

### Чат и броски

| Команда | Данные | Событие |
|---------|--------|---------|
| `chat.send` | `{ "text", "to"? }` — `to`: 1–20 `playerId` участников кампании (не удалённых, без автора) для личного сообщения | `chat.message` |
| `roll.request` | `{ "formula", "visibility", "label"? }` (`label` до 100 символов) | `chat.message` (`kind: "roll"`) |
| `chat.history` | `{ "before": "<messageId>", "limit"? }` (`limit` 1–100, по умолчанию 50) | — (ответ `ack { "messages": [ …ChatMessage… ] }`, видимые получателю, по возрастанию времени) |

`ChatMessage`:
```jsonc
{
  "id": "01J…", "createdAt": 1760530000000, "authorPlayerId": "01J…",
  "kind": "text",                // text | roll | system
  "visibility": "public",        // public | private | gm | self | blind
  "to": [ "01J…" ],              // только для private
  "text": "Иду к двери",         // для text и system; до 2000 символов
  "roll": { "formula", "label", "result": <dice.Result> } // для roll
}
```
Отрисовка для получателя:
- `public` — всем;
- `private` — автору и адресатам (`to`); **мастер чужую личную переписку не видит**, если он не адресат; остальным — `sync.noop`;
- `gm` (бросок) — автору и мастеру; `self` — только автору; `blind` — мастеру полностью, автору — сообщение **без** `roll.result` (видно, что бросок сделан), остальным — `sync.noop`.

Формулы и результат — по [vtt.md](../systems/vtt.md) («Формулы бросков»); ошибка разбора — `error` `bad_request` с `message` = текст ошибки разбора. Чат и история — по всей кампании, а не только текущей игровой сессии. Видимость броска от мастера работает так же (мастер-автор `blind` видит результат, потому что он мастер).

### Ограничения частоты в M1

Сверх общего лимита соединения (см. «Правила»): `token.drag` и `ruler.update` — не больше 30 в секунду каждый; лишние **молча отбрасываются** (без `rate_limited` и без серии отказов: это преходящие сообщения). `roll.request` — не больше 5 в секунду; сверх — `error` `rate_limited` на каждую лишнюю команду (в серию отказов общего лимита не входят).

### Ошибки команд M1

`forbidden` — нет прав (не мастер, не владелец, фишка `locked`, игрок трогает неактивную сцену); `not_found` — нет сцены, фишки, рисунка; `conflict` — удаление активной сцены, предел операций тумана; `bad_request` — поля вне ограничений (`data-model.md`).

## Правила

- Сервер **всегда** проверяет права, клиентским проверкам не доверяем.
- Кубики бросает сервер (`crypto/rand`), клиент только отображает результат.
- Rate limit на соединение: 50 сообщений/с в среднем, всплеск до 100 (token bucket); отдельные лимиты команд M1 — в «Ограничения частоты в M1». Ответ `error` `rate_limited` приходит только на **первый** отказ серии; остальные сообщения серии молча отбрасываются, чтобы ответы не усиливали флуд. Отказы складываются в **серию**: она продолжается, пока между соседними отказами меньше 1 секунды, и пропущенные сообщения между отказами её **не** обрывают (иначе при равномерном переполнении токен каждые 20 мс обнулял бы серию и `4029` не наступал бы никогда). Серия длиной 5 секунд — закрытие `4029`; пауза без отказов от 1 секунды начинает серию заново.
- Тайм-аут простоя измеряется таймером, который сбрасывает каждое входящее сообщение, а не дедлайном чтения: отмена чтения в `coder/websocket` рвёт соединение без кадра закрытия, и клиент не получил бы `4008`.
- Очередь отправки на соединение — размер буфера продолжения + 64 (сейчас 1064 сообщения), чтобы досылка всего буфера при продолжении не переполняла её; все ответы и события идут через неё одной горутиной записи, поэтому порядок сохраняется. Переполнение — закрытие `1013`.
