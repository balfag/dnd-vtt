# Отчёт spike #8: доступность извне

Дата: 2026-10-31. Issue: [#8](https://github.com/balfag/dnd-vtt/issues/8). Код: эта папка ([README](README.md)).

## Коротко

1. **Браузерный WebRTC нельзя пустить через HTTP-туннель** (Cloudflare Quick Tunnel, `ngrok http`): вариант B из `networking.md` нереализуем. В TURN нет WebSocket-транспорта, а браузер принимает только `turn:`/`turns:` с UDP/TCP/TLS. HTTP-туннель пропускает лишь HTTP и WebSocket.
2. **Реальны два пути медиа:** A — туннель с UDP (playit.gg, нужен аккаунт и внешний агент) и C — ICE-TCP через любой TCP-туннель (bore без аккаунта, ngrok tcp с проверкой карты). Локально проверено: Chromium **сам** подключается по TCP к пассивному кандидату сервера при полностью отсутствующих UDP-сокетах на сервере.
3. **Встроенный TURN не нужен.** Наш сервер сам является медиа-конечной точкой, поэтому ICE-TCP passive даёт то же самое проще (меньше портов, быстрее первый кадр). `turn-tcp` оставлен только как эксперимент.
4. **HTTPS в режиме проброса:** лучший кандидат — Let's Encrypt через `autocert` и имя `<ip-через-дефисы>.sslip.io` (HTTP-01 на порту 80). Но `sslip.io`/`nip.io` **нет в Public Suffix List**, поэтому лимит 50 сертификатов в неделю общий на всех их пользователей; на практике им подняли лимит (по их словам), но это зависит от доброй воли Let's Encrypt. Запасной вариант — самоподписанный сертификат с предупреждением. Не проверено внешним тестом (сценарий (д)).
5. **Безопасность:** текущая `isLoopback` **недостаточна** для сырых TCP-туннелей (bore, ngrok tcp, playit, frp tcp): они не добавляют никаких заголовков, а агент подключается с `127.0.0.1`. Предложение — раздел «Безопасность».
6. **Ограничения самого замера:** все числа ниже получены на одном ПК через `localhost`, без реальной сети. Это проверка работоспособности режимов, а не прогноз задержки в интернете. Внешние сценарии не выполнялись.

## 2. Медиа через туннель

### Может ли браузерный WebRTC использовать TURN поверх WebSocket

**Нет.** Подтверждено:

- [RFC 8656 §3.1](https://www.rfc-editor.org/rfc/rfc8656#section-3.1): между клиентом и TURN-сервером допустимы UDP, TCP, TLS поверх TCP и DTLS поверх UDP; WebSocket в списке нет (в прочитанной части RFC он не упоминается).
- [RFC 8835](https://www.rfc-editor.org/rfc/rfc8835) (транспорты WebRTC): браузеры обязаны поддерживать TURN поверх TCP и поверх TLS.
- В `RTCIceServer` браузера есть схемы `turn:`/`turns:` с `?transport=udp|tcp`; схемы `ws:`/`wss:` нет. Эмпирически (Chromium, этот spike): `turn:…?transport=tcp` + `iceTransportPolicy: "relay"` работает, но **только плечо клиент↔TURN идёт по TCP**; плечо TURN↔пир всегда UDP (в `getStats` локальный кандидат выбранной пары — `prflx/udp(tcp)`, т. е. UDP-кандидат, полученный через TCP-соединение с TURN).

Подсказка архитектора подтверждена. WebSocket-туннелю такой TURN не подходит: нужен сырой TCP-порт.

### Что пропускает HTTP-туннель

Cloudflare Quick Tunnel: HTTP и WebSocket, **SSE не поддерживается**, до 200 запросов в полёте ([документация](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/)). Сырого TCP и UDP нет. `ngrok http` — тоже только HTTP/WS. Медиа WebRTC через них не пройдёт. Теоретически можно гнать видео по WebSocket собственным протоколом (WebCodecs), но это не WebRTC, уходит из рамок spike и теряет SFU-схему из `voice-video.md`.

### ICE-TCP через TCP-туннель

- Браузеры собирают **только активные** TCP-кандидаты и сами подключаются к пассивному кандидату сервера ([RFC 6544](https://www.rfc-editor.org/rfc/rfc6544); для Firefox — [блог Mozilla](https://blog.mozilla.org/webrtc/)). **Проверено для Chromium:** при `-mode=tcp` сервер не открывает ни одного UDP-сокета (проверено `Get-NetUDPEndpoint` — пусто), а выбранная пара — `prflx/tcp` ↔ `host/tcp`. Активные TCP-кандидаты **не видны** в SDP браузера (локальный SDP содержит только UDP), но соединение устанавливается — Chromium использует их как peer-reflexive.
- Кандидат сервера должен указывать **публичный адрес и порт туннеля**. pion (`ICEAddressRewriteRule`/`SetNAT1To1IPs`) подменяет только IP; порт остаётся локальным. Поэтому в прототипе ответ SDP правится текстом: к первому host-кандидату каждого компонента добавляется копия с адресом из `-advertise` (host:port). Имя резолвится на сервере, потому что нет гарантии, что браузер резолвит имена в удалённых кандидатах. Для `bore.pub:NNNNN` это работает без `SetNAT1To1IPs`.
- Наблюдение: правило `SetICEAddressRewriteRules` с типом `srflx` при UDP mux опубликовало кандидат с **другим** портом (случайный, не порт mux) — поэтому прототип его не использует; для порта нужна правка SDP или собственный механизм в основном коде.
- Не проверено: Safari и Firefox (только Chromium); одновременная работа UDP mux и TCP mux на одном номере порта в одном процессе (в прототипе режимы раздельные).

## 3. Локальный эксперимент: медиа по TCP

Среда: Windows 11, Go 1.26.1, pion/webrtc v4.2.23, Chromium из Playwright (chromium-1243) с `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream`, скрипт вне репозитория. Источник — canvas 640×360, 30 к/с, VP8, с движущимися фигурами и «штрихкодом» времени (24 бита, `performance.timeOrigin + now`). Эхо-кадр читается из принятого видео, задержка = момент показа − метка в кадре. Один прогон на режим, 15 с замера, всё через `localhost`.

| Режим | Соединилось | ICE до `connected` | До первого кадра | Задержка эха (мс): мин / p50 / p95 / макс, n | CPU сервера за 15 с | Выбранная пара (браузер) | Потери |
|-------|-------------|--------------------|------------------|-----------------------------------------------|----------------------|---------------------------|--------|
| `udp` | да | 164 мс | 200 мс | 17 / 35 / 51 / 69, n=419 | 0,28 с = 1,7 % ядра | host/udp ↔ host/udp | 0 |
| `tcp` | да | 166 мс | 196 мс | 16 / 37 / 51 / 62, n=437 | 0,17 с = 1,1 % ядра | prflx/tcp ↔ host/tcp | 0 |
| `turn-tcp` | да | 172 мс | 245 мс | 16 / 37 / 51 / 67, n=409 | 0,31 с = 1,9 % ядра | prflx/udp(tcp) ↔ host/udp | 0 |

Как читать:

- Все три режима соединяются и несут видео без потерь. Разницы по задержке нет — на `localhost` нет потерь пакетов, очереди и RTT; **преимущества/недостатки TCP (блокировка очереди при потерях, рост задержки) этим замером не видны**. Реальная задержка зависит от канала и покажется только во внешних сценариях.
- В `turn-tcp` дольше первый кадр (245 мс против ~200) и нужны ещё 50 UDP-портов для relay на loopback — лишнее для встроенного SFU.
- RTT WebSocket на localhost: p50 0,2 мс (во всех режимах).
- CPU — только сервер, кодирования нет (пересылка RTP): 1–2 % одного ядра на один поток 640×360. Для 8 камер это порядка 8–16 %, оценочно; в spike #7 есть измерения SFU.
- Измерение CPU — `TotalProcessorTime` процесса за время сессии, без повторов; погрешность не оценивалась.
- Проверка параметров из ловушек: UDP-сокеты в режиме `tcp` отсутствуют; TCP-кандидаты браузер пробует сам.

Дополнительно проверено: `-tls` (HTTPS/WSS на том же порту) — эхо работает, браузер запущен с `--ignore-certificate-errors`; ответ SDP с `-advertise` содержит добавленные кандидаты `adv1`/`adv2` с нужными адресом и портом (проверено разбором лога; соединение с вымышленным адресом, естественно, не устанавливалось, и браузер выбрал настоящий).

## 4. HTTPS при пробросе портов

`getUserMedia` требует secure context: HTTPS или `localhost`. Туннель даёт HTTPS сам; при пробросе портов нужен свой сертификат.

### Варианты

| Вариант | Предупреждение браузера | Требования | Лимиты / риски |
|---------|-------------------------|-----------|----------------|
| Самоподписанный (`-tls`) | **да**, у каждого игрока при первом входе (на телефонах бывает неочевидно, как принять) | ничего | нет лимитов; WSS работает после принятия |
| Let's Encrypt + `sslip.io`/`nip.io` | нет | порт 80 (HTTP-01) или 443 (TLS-ALPN-01) достижимы из интернета; имя `203-0-113-5.sslip.io` указывает на IP сам | см. ниже: общий лимит; IP мастера меняется → имя меняется → новый сертификат |
| DDNS (DuckDNS и др.) + HTTP-01 | нет | аккаунт у DDNS (DuckDNS: вход через Google/GitHub/Reddit и т. д., токен), порт 80/443 | у `duckdns.org` свой счёт лимитов (в PSL); постоянное имя |

### Лимиты Let's Encrypt (на 2026-10-31, [документация](https://letsencrypt.org/docs/rate-limits/))

| Лимит | Значение |
|-------|----------|
| Сертификатов на **зарегистрированный домен** (или IPv4-адрес, или IPv6 /64) | **50 за 7 суток** (глобальный, считается по всем аккаунтам) |
| Сертификатов на точный набор имён | 5 за 7 суток (глобальный) |

Зарегистрированный домен Let's Encrypt определяет по Public Suffix List.

### Статус в Public Suffix List

Проверено по файлу `public_suffix_list.dat` из ветки `main` [publicsuffix/list](https://github.com/publicsuffix/list) (скачан 2026-10-31):

| Домен | В PSL |
|-------|-------|
| `sslip.io` | **нет** |
| `nip.io` | **нет** |
| `duckdns.org` | да |
| `dynv6.net`, `ddns.net`, `hopto.org`, `zapto.org`, `no-ip.org` | да |
| `trycloudflare.com`, `ngrok.io`, `ngrok.app`, `ngrok-free.app`, `ts.net` | да |

Следствие: у `sslip.io` и `nip.io` **один общий** лимит 50 сертификатов/7 суток на весь домен для всех пользователей мира. По словам [nip.io](https://nip.io/), Let's Encrypt поднимал им лимит (с 50 до 250 000 за годы, от 500 000 отказал), и сайт советует при упоре в лимит переключаться на соседний домен (sslip.io ↔ nip.io) или брать IP-сертификат. То есть работает, но «на честном слове» отдельного исключения. Подстановочные сертификаты они не поддерживают. У DuckDNS (`duckdns.org` в PSL) лимит у каждого поддомена свой.

### Порты

- HTTP-01 — порт **80** (`autocert` слушает его через `HTTPHandler`).
- TLS-ALPN-01 — порт **443** (`autocert` отвечает на него на том же listener).
- Достаточно одного из двух; `autocert` пробует оба. Для режима проброса это дополнительные порты (80 и/или 443), а не 7777: мастеру придётся пробрасывать 443 → ПК или менять порт HTTPS. На нестандартном порту (7777) проверка Let's Encrypt не пройдёт — проверяются только 80/443.
- Если провайдер блокирует 80/443 (бывает на домашних тарифах) — остаётся DNS-01 (нужен клиент вместо `autocert`) или самоподписанный.

### Прототип

`tls/` — `autocert.Manager` с `HostWhitelist` на одно имя, `DirCache`, флаг `-staging` (staging CA, без лимитов). Без `-domain` и `-cache` не запускается (проверено, код выхода 2). Не запускался против Let's Encrypt — это сценарий (д).

## 5. Безопасность loopback при туннеле

Текущая проверка (`internal/httpapi/respond.go`): запрос локальный, если IP соединения — loopback и нет `X-Forwarded-For` и `Forwarded`.

| Туннель | Агент подключается с | Заголовки | Что видит `isLoopback` |
|---------|------------------------|-----------|--------------------------|
| Cloudflare (Quick/Named) | `127.0.0.1` | `X-Forwarded-For` и `Cf-Connecting-Ip` присутствуют | отказ — верно |
| `ngrok http` (агент) | `127.0.0.1` | `X-Forwarded-*` по умолчанию, но **пользователь может убрать** флагом | при удалении заголовков — «локально» (неверно) |
| `ngrok tcp`, bore, playit, frp tcp | `127.0.0.1` | **никаких** | **«локально» — неверно**, для любого запроса из интернета |
| frp http | `127.0.0.1` | `X-Forwarded-For` | отказ — верно |
| `ngrok-go`, `tsnet` | не loopback (адрес издателя соединения) | — | отказ — верно |

Вывод: **проверки по заголовкам недостаточно**. Любой сырой TCP-туннель превращает всех посетителей в «локальных» (повышение привилегий: `/setup`, обмен GM-токена). Смягчение — одноразовые токены (setup-токен, GM-токен на 10 минут), но защита не должна опираться только на них.

### Предложение

1. **Отдельный listener для привилегированных маршрутов.** `/setup`, `POST /api/setup`, `POST /api/auth/gm-token` обслуживаются только на `127.0.0.1:<случайный порт>`, который **никогда** не пробрасывается и не отдаётся туннелю. Публичный порт 7777 их не знает (404). Агент туннеля настроен на 7777, а не на служебный порт — мастер не может ошибиться, т. к. порт не показывается.
2. **Явный флаг «внешний доступ включён»** (в конфиге/UI). Пока он включён, `isLoopback` на публичном порту всегда `false`, независимо от адреса и заголовков. Сегодняшние проверки заголовков остаются как вторая линия.
3. Дополнительно требовать `Host` из набора `localhost`, `127.0.0.1`, `[::1]` (защита от DNS rebinding и от случайного проксирования). Заголовок `Host` подделывается сырым TCP-посетителем, поэтому это не замена пунктам 1–2.
4. `X-Forwarded-For`/`Cf-Connecting-Ip` как источник IP игрока (для журнала и ограничения частоты) принимать, только когда внешний доступ включён **и** туннель — один из известных; иначе игнорировать.
5. Для встроенных библиотек (`ngrok-go`, `tsnet`) соединения уже не loopback — но флаг из п. 2 всё равно включается, чтобы не зависеть от особенностей.

Проверить на живых туннелях: `GET /headers` у прототипа возвращает `remoteAddr`, все заголовки и `currentIsLoopback`; эти поля записываются в сценариях (б)–(г).

## 6. Внешние тесты (для владельца)

Общее. Собрать: `cd spikes/connectivity; go build -o media.exe ./media; go build -o tls.exe ./tls`. Ничего ставить в систему не нужно, кроме агентов туннелей в сценариях. Брандмауэр Windows спросит разрешение на сетевой доступ — разрешите для частных и публичных сетей. Камера: на телефоне страница должна быть открыта по **HTTPS**; для сценариев (а), (в), (г) запускайте `media.exe` с `-tls` и принимайте предупреждение браузера, или используйте HTTPS-адрес Cloudflare. Если камеры нет или не нужна — страница без `?camera=1` шлёт тестовый узор, а `?camera=1` включает камеру.

Что записывать в каждом сценарии: соединилось ли (поле `connected`), `ttffMs` (до первого кадра), `latency` (мин/p50/p95/макс) и `pair` (тип выбранной пары) из JSON в блоке под видео, `ws` (RTT WebSocket), время суток и сеть (дом/мобильная). Если не соединилось — скопируйте строки `ice … failed` и `local candidates`.

### (а) Проброс портов + вход с телефона по мобильной сети

Предусловия: у роутера белый IP (сравните внешний IP из `https://ifconfig.me` с WAN-адресом в роутере; если они разные или WAN в диапазоне `100.64.0.0/10` — это CGNAT, проброс невозможен, запишите это и переходите к (в)/(г)).

1. В роутере: `TCP 7777 → <LAN-IP ПК>:7777`, `UDP 7778 → <LAN-IP ПК>:7778`, `TCP 7778 → <LAN-IP ПК>:7778`.
2. Узнайте внешний IP: `curl.exe -s https://ifconfig.me`.
3. Запуск (режим UDP): `.\media.exe -mode=udp -http :7777 -media-port 7778 -advertise <ВНЕШНИЙ_IP>:7778 -tls -tls-host <ВНЕШНИЙ_IP>`
4. Телефон — **мобильная сеть, не Wi-Fi**: `https://<ВНЕШНИЙ_IP>:7777/?camera=1`, принять предупреждение, **Start echo**.
5. Повторить в режиме TCP: `.\media.exe -mode=tcp -http :7777 -media-port 7778 -advertise <ВНЕШНИЙ_IP>:7778 -tls -tls-host <ВНЕШНИЙ_IP>`.
6. Записать для `udp` и `tcp`.

Если со своей же сети (Wi-Fi) страница по внешнему IP не открывается — это hairpin NAT роутера, не ошибка; проверяйте только с мобильной сети.

### (б) Cloudflare Quick Tunnel к HTTP-серверу

Скачать `cloudflared` с [GitHub cloudflare/cloudflared](https://github.com/cloudflare/cloudflared) (аккаунт не нужен).

1. `.\media.exe -mode=udp`
2. В другом окне: `cloudflared tunnel --url http://localhost:17777` — выведет `https://<случайное>.trycloudflare.com`.
3. Открыть `https://<…>.trycloudflare.com/headers` и **сохранить JSON целиком** (особенно `remoteAddr`, `headers`, `currentIsLoopback`).
4. Открыть главную `https://<…>.trycloudflare.com/`, нажать **WebSocket RTT**: работает ли WebSocket, p50/p95 (в блоке `ws rtt`). Сравнить с RTT до `/headers` через `curl.exe -s -o NUL -w "%{time_total}" <url>`.
5. Нажать **Start echo**: ожидаем сбой ICE (медиа через HTTP-туннель не идёт) — записать, что произошло (`ice failed`, время до ошибки).
6. Желательно повторить с телефона (камера по HTTPS работает), `?camera=1`.

### (в) TCP-туннель (bore или ngrok tcp) + режим `tcp`

Вариант 1 — bore (без аккаунта). Скачать релиз [bore](https://github.com/ekzhang/bore/releases) или `cargo install bore-cli`.

1. `.\media.exe -mode=tcp`
2. `bore local 17778 --to bore.pub` — выведет `listening at bore.pub:NNNNN`.
3. Перезапустить сервер с адресом туннеля: `.\media.exe -mode=tcp -advertise bore.pub:NNNNN`.
4. Веб-страницу открыть по HTTPS любым способом: Cloudflare-туннель из (б) (`cloudflared tunnel --url http://localhost:17777`, открыть его адрес с телефона **по мобильной сети**) — так проверяется гипотеза D (веб через Cloudflare + медиа через bore).
5. **Start echo** (`?camera=1` с телефона). В `pair` должно быть `…/tcp`. Записать `ttffMs` и `latency`.

Вариант 2 — ngrok tcp (аккаунт + привязка карты, списаний нет). Установить ngrok, добавить authtoken.

1. `ngrok tcp 17778` — выведет `tcp://N.tcp.<регион>.ngrok.io:PPPPP`.
2. `.\media.exe -mode=tcp -advertise N.tcp.<регион>.ngrok.io:PPPPP`.
3. Страница — как в варианте 1 (Cloudflare для HTTPS).

Записать для каждого: соединилось, `ttffMs`, задержку, и заметна ли разница с `udp`.

### (г) playit.gg с UDP + режим `udp`

Зарегистрироваться на [playit.gg](https://playit.gg/), скачать агент, привязать его к аккаунту.

1. В панели playit создать **Custom UDP** туннель на локальный порт `17778`; записать выданный `адрес:порт`.
2. `.\media.exe -mode=udp -advertise <адрес>:<порт>`
3. Страницу открыть по HTTPS через Cloudflare (как в (в)) **или** создать в playit TCP-туннель на `17777` и открыть выданный адрес (HTTP; камера не включится — используйте `-tls` и примите предупреждение). Отдельно **запишите**, даёт ли бесплатный план HTTPS-туннель (по вторичным источникам — только Premium) и сколько туннелей разрешено.
4. Телефон по мобильной сети: **Start echo**. Записать `connected`, `ttffMs`, `latency`, `pair` (должна быть `…/udp`).
5. Записать лимиты бесплатного плана, показанные в панели.

### (д) `autocert` с `sslip.io`

Нужно: проброс **TCP 80 → ПК:80** и **TCP 443 → ПК:443**, внешний IP из `https://ifconfig.me` (например `203.0.113.5`).

1. Имя: `203-0-113-5.sslip.io` (точки заменить на дефисы). Проверить: `nslookup 203-0-113-5.sslip.io` возвращает ваш IP.
2. Сначала staging (лимиты щедрые): `.\tls.exe -domain 203-0-113-5.sslip.io -cache C:\acme-staging -staging`. Открыть `https://203-0-113-5.sslip.io/` с телефона по мобильной сети. Ожидание: браузер ругается (staging CA не доверенный) — но в логе сервера должно появиться успешное получение сертификата. Записать время до успеха.
3. Боевой: `.\tls.exe -domain 203-0-113-5.sslip.io -cache C:\acme-prod`. Открыть то же. Записать: выдан ли сертификат, **есть ли предупреждение браузера**, время первого ответа, сообщения об ошибках (`rateLimited` — запишите, это важный результат).
4. Если не вышло: попробовать `203-0-113-5.nip.io`.
5. Повторить пункт 3 после перезапуска — сертификат берётся из кэша (нет нового заказа).

## 7. Рекомендация

По умолчанию — **ручной проброс портов с UDP** (`7777/tcp` + `7778/udp`) и ICE-TCP passive на том же номере порта как фолбэк: без аккаунтов, минимальная задержка, не зависит от сторонних сервисов. Это подтверждается только локально; (а) должен подтвердить на практике.

Когда проброс невозможен (CGNAT, чужой роутер):

1. **Туннель без аккаунта (гипотеза D):** веб (HTTPS, WebSocket) — Cloudflare Quick Tunnel; медиа — ICE-TCP через `bore` или, при наличии аккаунта, `ngrok tcp`. Требуется два агента, адрес медиа-туннеля нужно подставлять в кандидат (`-advertise` в прототипе). Минус: задержка и пропускная способность TCP, `bore.pub` — публичный сервер без гарантий.
2. **playit.gg:** единственный вариант с UDP на бесплатном аккаунте; один внешний агент и аккаунт; HTTPS на бесплатном плане под вопросом.

HTTPS в режиме проброса: **Let's Encrypt + `sslip.io`/`nip.io`** (HTTP-01), запасной — самоподписанный сертификат с понятной инструкцией в мастере подключения. Решающий довод — результат (д).

Что встраиваем: автогенерация самоподписанного сертификата, `autocert`, ICE-TCP mux и UDP mux в SFU, подстановка внешнего адреса/порта в кандидаты (с правкой SDP), `/headers`-подобная диагностика в мастере подключения, внешний listener для привилегированных маршрутов. **Не встраиваем:** TURN (не нужен), агентов туннелей (запускаются как sidecar по явной просьбе мастера; скачивание только с его согласия, лицензии: cloudflared — Apache-2.0, bore — MIT, playit — BSD-2; все совместимы с AGPL-3.0 при запуске как отдельный процесс). `ngrok-go` (MIT) и `tsnet` можно встроить, но оба требуют аккаунта и не дают UDP — в M0 не нужны.

Влияние на архитектуру: абстракция `netx.Exposure` из ADR-0005 должна уметь «публиковать» отдельно веб-адрес и медиа-адрес (с разными схемами, хостами и портами) — в туннельном режиме это разные агенты.

## 8. Проект ADR-0005 (раздел «Решение»)

> **Решение (проект, после внешних тестов (а)–(д))**
>
> 1. Сервер слушает один HTTP(S)-порт (по умолчанию `7777/tcp`) и один медиа-порт (по умолчанию `7778`): UDP — ICE UDP mux, TCP — ICE-TCP passive (фолбэк, тот же номер). Встроенный TURN не используется.
> 2. Режимы подключения: **(1) проброс портов** — по умолчанию; **(2) туннель** — запасной, через сторонний агент как sidecar (Cloudflare Quick Tunnel для веба, TCP-туннель `bore`/`ngrok tcp` или `playit.gg` для медиа). HTTP-туннели не пропускают WebRTC, поэтому медиа всегда идёт отдельным путём. TURN-over-WebSocket невозможен (в RFC 8656 нет такого транспорта).
> 3. Внешний адрес и порт медиа публикуются в ICE-кандидатах отдельно от адреса веб-страницы (абстракция `netx.Exposure`); для туннелей порт отличается от локального, поэтому ответ SDP дополняется кандидатом с адресом туннеля.
> 4. HTTPS в режиме проброса: Let's Encrypt через `autocert` и имя `<ip>.sslip.io` (порты 80/443), запасной вариант — самоподписанный сертификат. В режиме туннеля HTTPS даёт туннель.
> 5. Безопасность: привилегированные маршруты (`/setup`, обмен GM-токена) обслуживаются только отдельным loopback-listener'ом, который не пробрасывается и не отдаётся туннелю; при включённом внешнем доступе `isLoopback` на публичном порту всегда `false`. Заголовки `X-Forwarded-*` и `Cf-Connecting-Ip` принимаются только в туннельном режиме.
> 6. Агенты туннелей не вшиваются; скачиваются и запускаются по явному согласию мастера. Лицензии (Apache-2.0, MIT, BSD-2-Clause) совместимы с AGPL-3.0 при запуске отдельным процессом.

## Что осталось неизвестным

- Все внешние сценарии (а)–(д).
- Реальная задержка ICE-TCP и TURN/TCP в интернете: локальный замер её не показывает.
- Поведение Firefox и Safari при ICE-TCP; одновременная работа UDP и TCP mux в одном процессе.
- Условия бесплатного плана playit.gg (HTTPS, число туннелей) и заголовки `tailscale funnel` на локальный порт — нет на официальных страницах, прочитанных в spike.
- Лицензии, помеченные †, и необходимость домена для именованного Cloudflare Tunnel.
- Сертификаты для IP-адресов (профиль `shortlived`): `autocert` не поддерживает, свой менеджер не писался.
